Robotics · Portfolio strategy

Build a robotics portfolio that makes your technical evidence easy to evaluate.

A portfolio should not try to look like you already worked at a large industrial company. It should make the work you genuinely completed understandable, reproducible and relevant to the role you want.

Reviewed: 11 September 2026Career-practice reference: Make it in Germany6 min read

Start from the vacancy, not from a technology shopping list

The German Federal Government’s Make it in Germany guidance tells job applicants to read the vacancy carefully and tailor their application to the requested documents and role. Apply the same principle to your technical portfolio: if the target role is embedded control, a beautiful computer-vision demo may be less valuable than a smaller project showing timing, interfaces, testing and hardware constraints.

What counts as useful evidence

A good project answers five questions quickly: What problem did you solve? What did you personally build? How is the system structured? How did you test it? What evidence shows the result?

  • Repository with understandable structure and setup instructions.
  • Architecture or data-flow diagram.
  • Short demo video or GIF where motion or interaction matters.
  • Test results, logs or evaluation plots where appropriate.
  • Known limitations and next steps.
  • Clear distinction between your work and third-party frameworks or starter code.

Simulation is valid when you describe it honestly

You do not need an industrial robot to demonstrate every robotics skill. Gazebo, Webots, MATLAB/Simulink, ROS 2 and PLC simulation environments can produce meaningful evidence when the project tests a real technical question. The key is to state that the result is simulated and avoid presenting simulation as physical deployment.

Never convert a simulation into a fake hardware claim. “Validated in Gazebo with recorded ATE/RPE metrics” is stronger than implying a physical robot was tested when it was not.

For robotics and autonomy projects

Useful evidence can include coordinate frames, sensor assumptions, maps, trajectories, latency, failure cases, parameter choices and reproducible evaluation. A SLAM project is more credible when it shows the dataset or simulation environment and the evaluation method rather than only a screenshot of RViz.

For automation and PLC projects

Tools such as TwinCAT, TIA Portal or CODESYS can be useful when they match the target role, but the brand name alone is not evidence. Show the control problem, sequence logic, state transitions, safety assumptions, I/O model and test behaviour. If the system is simulated, label it clearly.

For embedded systems

Document interfaces, timing constraints, memory/CPU considerations, sensor or actuator behaviour, error handling and how the firmware was tested. Even a small board-level project can be strong if the engineering decisions are visible.

Write READMEs for technical reviewers

  1. One-sentence purpose: what the system does.
  2. Evidence preview: one image, GIF or result table near the top.
  3. Architecture: major components and data flow.
  4. Reproduction: requirements, setup and exact run steps.
  5. Evaluation: what was measured and how.
  6. Limitations: what remains unvalidated.

Do not fabricate “recruiter rules”

There is no universal rule that every German employer will inspect GitHub in 30 seconds, value projects above university background, or require a particular simulator. Employers differ. The portfolio is valuable because it gives an interested technical reviewer better evidence—not because it guarantees that every recruiter will inspect it.

Build fewer, stronger projects

For most early-career engineers, three strong projects aligned to target roles are more useful than a long list of shallow demos. Improve the evidence, documentation and evaluation on projects that already match your direction before creating another repository simply to increase project count.
